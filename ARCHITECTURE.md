# Architecture

## Current implementation

ClipPulse is split into three local layers:

1. **Electron main process** (`src/main`) owns native dialogs, project and media file access, FFmpeg process execution, and renderer IPC.
2. **Core editing engine** (`src/core`) owns the versioned project model, validation, rational time arithmetic, media probing/import, timeline edits, and rendering. The CLI and desktop app call the same core functions.
3. **React renderer** (`src/renderer`) presents the media bin, source preview, timeline, transport, and inspector. It cannot access Node.js or arbitrary filesystem APIs directly; operations go through a narrow preload bridge.
4. **Agent adapters** (`src/main/agent.ts`, `agentRest.ts`, `agentMcp.ts`) expose the same core as versioned CLI JSON, optional loopback REST, and MCP stdio. They validate typed inputs, serialize edits per project, enforce explicit filesystem roots, negotiate MCP protocol versions, and return serializable project/render state.

The desktop API is Electron IPC. The CLI, local REST service, and MCP server are stable headless interfaces; see `AGENT_API.md` and `config/agent-api-v1.schema.json`.

## Project and time model

An `.omproj` is a JSON document with `schemaVersion`, output profile, media records, tracks, and clips. Clip times are reduced rational seconds (`{ "num": "5", "den": "2" }` means 2.5 seconds), stored as decimal strings so integer arithmetic can use `BigInt` without float drift. The project frame rate is also rational (for example, `30000/1001`). UI timing edits snap to exact project frames; the CLI accepts decimal or `numerator/denominator` time values.

Imported assets retain their absolute source path, basic FFprobe metadata, a SHA-256 content identity, and a cached preview image named by content hash. Video assets use a thumbnail frame; audio-only assets use a local FFmpeg `showwavespic` image on media cards. Audio-track clips get separate source-trimmed waveform images sized for the active timeline zoom. Import never copies, transcodes, or modifies the source. Derived files and the persistent media-job queue are stored in a project-adjacent `.openmontage-cache-<project-id>` directory.

That cache also contains a SQLite index for import roots, media metadata, tags, favorites, and game names. When a file's path, size, and modification timestamp match an indexed record, re-import reuses its metadata without probing or hashing the file again. Changed files are hashed and exact duplicates are detected across paths. Folders explicitly selected for import are watched with a debounced local filesystem watcher; the media panel can pause or resume each root. The `.omproj` remains the project state and the SQLite index can be rebuilt.

Missing source paths are checked when a project opens. Relinking a file requires the same media kind and enough duration for all existing clip source ranges; it updates metadata and content-addressed thumbnails while retaining the media ID, so clip references remain valid. Relinking to different source content clears audio-analysis caches and cancels/removes old-content proxy and clip-waveform results.

Proxy and clip-waveform jobs use a project-persistent JSON queue. Running work is returned to the queued state after restart; users can pause/resume the queue or retry failed jobs. Only one derived-media FFmpeg process runs at once, using one thread. Proxies are limited to 960×540, 1.5 GB per file, and 12 GB per project; clip waveforms are capped at 16,384 pixels and the waveform cache at 512 MiB. Completed video proxies are used by the Source monitor; timeline preview and final export still read original media.

Edits are non-destructive: clips refer to media and record a timeline start, source in point, duration, and audio/effect settings. Optional clip fields add rational playback rates and speed keyframes, video transforms, color controls and LUT paths, animated properties, transitions, and title overlays while older project files continue to load. Splits and trims preserve or rebase animation timing and source coverage. Saving writes a temporary JSON file and renames it into place. Before replacement the previous project becomes `<project>.bak`; a project-adjacent history journal stores up to 50 complete states with a cursor for persistent undo/redo. Restoring a snapshot also synchronizes project media metadata in SQLite so tags and favorites follow undo/redo.

## Export path

The renderer builds one FFmpeg filter graph from project state. A generated black canvas establishes the output profile. `src/core/clipEffects.ts` builds the common clip filters used by export and still preview. Video clips are source-trimmed, mapped through integrated playback-rate curves, frame-rate converted, transformed and color-adjusted, then overlaid in track order. Alpha dissolves and directional wipes compose over lower tracks; `drawtext` applies title overlays with an available system font or a project-selected font file. LUT files are read-only inputs. Audio clips are source-trimmed, pitch-preserving tempo-adjusted in short sections for ramps, faded, optionally loudness-normalized, and gain-automated. Track audio roles form dialogue/music buses so `sidechaincompress` can duck music. The final mix is limited. FFmpeg encodes H.264/AAC into a temporary MP4; FFprobe checks that the result has a video stream before the file is installed at the requested path. Source overwrite is rejected.

The Timeline monitor requests a frame-snapped still image from `renderTimelineFrame` when the playhead moves. It seeks to the speed-adjusted source frame, applies the same clip video filters as export, composites active, unmuted video clips over black in the same track order, and caches frames under the project cache. The Source monitor plays a completed proxy when one exists, otherwise it plays the original source. Timeline playback renders a revision-cached MP4 through the export graph and plays that file; playback is not live during editing. Synthetic-media parity tests compare representative timeline-preview frames with exported frames and exercise transition and audio boundaries.

`src/core/qualityAnalysis.ts` audits the existing project model and sampled `renderTimelineFrame` outputs, reports objective checks separately from measured heuristics, and optionally renders the actual timeline to inspect audio peaks, level jumps, and sustained near-silence. Exact rational timeline positions and compact track/clip snapshots are included in each report. The agent API persists reports and protected preview frames in the project cache. `quality_improve` applies only short, structurally bounded video-gap fixes through the normal transaction and history path, then renders and checks again; failed verification restores both the project and its history. A visual aesthetic score is not inferred by the core analyzer.

## Security and reliability boundaries

- Renderer Node integration is disabled, context isolation and sandboxing are enabled, and the preload exposes explicit editing operations only.
- The desktop app itself listens on no network port. The optional agent REST service binds only to `127.0.0.1`, requires a bearer token, rejects browser-origin requests, and cannot be configured to bind remotely.
- Project operations validate references and source ranges before writing.
- Agent transactions persist a project/history recovery snapshot before the first edit. A later request restores an abandoned snapshot after process exit; active same-host transaction journals are left alone.
- Export writes to a temporary file and validates the output before finalizing.
- FFmpeg and FFprobe are external runtime dependencies, not bundled binaries.
- Agent adapters require explicit local root grants for project, source, effect-input, preview, and export paths. Recursive media imports reject symbolic links; sidecar cache/history paths are checked against the same grants.
- Media paths are local absolute paths. Portable project packaging remains future work.
- The application uses Node 24's built-in `node:sqlite` API for the local index; the desktop app and agent adapters currently require Node 24 or newer.

## Planned expansion

The audio analyzer (`src/core/audioAnalysis.ts`) computes centered 2,048-sample spectral-flux and RMS-change features at 256-sample hops, tempo/subdivision-aware autocorrelation hypotheses, overlapping local tempo estimates, and a dynamic-programming beat path that follows local tempo. Its v5 result keeps the legacy beat/downbeat arrays and adds a confidence-bearing beat grid, local tempo segments, distinct onset events and stronger accents, plus section-scale build-up/drop/quiet/section-change events. These scores are relative signal heuristics, not calibrated probabilities; local evaluation reports timing-tolerant precision/recall/F1, tempo error, and known failure cases against a frozen v4 implementation and local references. Meter/downbeat inference remains weak, and abrupt changes can be blurred by the overlapping tempo windows. Meter hypotheses combine bass, RMS, and beat strengths and include eighth-note meters; they are withheld when meter contrast is too weak. BPM is reported in quarter-note units when an eighth-note pulse is identified with stronger meter evidence. The v5 cache method invalidates old analysis once after an algorithm change. The `DetectorPlugin` interface in `src/core/highlightAnalysis.ts` is the extension point for local, model-backed, and game-specific detectors. Built-ins emit audio-activity, FFmpeg scene-change, sampled grayscale frame-difference motion, and optional Tesseract OCR cues. `src/core/gameplay/valorant.ts` provides a game-specific phrase classifier and normalized-coordinate OCR kill-feed-change cue. Only explicit recognized phrases produce explicit `kill`, `headshot`, `multi_kill`, `ace`, `clutch`, objective, or round-end labels; inferred 1vN states, feed changes, motion, audio, and low activity remain visibly heuristic, with uncertainties. Audio-plus-motion corroboration is labeled combat activity, never a verified kill. The pipeline keeps semantic event labels while grouping coincident detector signals, exposes score components, and caches by source metadata and detector versions. `src/core/analysisEvaluation.ts` reports per-event-type precision/recall/F1 and mean absolute timestamp error against versioned, locally supplied manifests, as well as the legacy time-only activity-cue baseline. The checked-in Valorant text fixture is parser regression data only; there are no annotated gameplay recordings or representative accuracy results in the repository. `src/core/analysisRuntimes.ts` reports FFmpeg/Tesseract availability and the no-gameplay-model fallback; the build contains no compatible gameplay inference adapter. `src/core/autoMontage.ts` combines cached music analysis, reviewed event windows, asset ratings, source-window constraints, music anchors, and configurable pacing/audio rules into explainable plans. Unreviewed quiet passages, unclassified text, and tentative kill-feed changes are excluded; users can accept or correct a candidate's type and time before using it. It materializes each plan as a new project with a fresh project ID and generated tracks, then writes that project and its plan report beside the selected output folder; it never edits the source project file. The desktop can open generated variants for shared timeline playback and export, while the CLI can inspect frames and export them. Scores remain transparent heuristics, not calibrated gameplay predictions. Phases E–G add shared effect/keyframe and compositing semantics plus typed agent adapters over these same core operations; no alternate editing engine is maintained.

OpenTimelineIO may be added for interchange, but it will not replace the FFmpeg rendering engine. The agent interfaces are thin validated adapters over these same core operations; no alternate editing engine is maintained.
